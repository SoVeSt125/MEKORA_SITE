# Правила MEKORA Intelligence · rules-1.0.0

Это детерминированная проверка условий, а не подтверждение конкретного дефекта.
Заключение содержит факт, причину срабатывания, ID измерений, ограничения,
рекомендуемые действия, версию и отметку демонстрационного источника.

| Правило | Срабатывание | Восстановление |
|---|---|---|
| Относительная вибрация | 3 последовательных свежих корректных RMS ≥ 2× утверждённой базы | 3 RMS ≤ 1,5× базы |
| Температурное ограничение | 3 температуры ≥ предела, заданного для двигателя | 3 температуры ≤ предел − 5 °C |
| Батарея | 3 значения ≤ 15% | 3 значения ≥ 20% |
| Потеря связи | Нет свежего измерения дольше `MEKORA_STALE_SECONDS` | Появилось свежее измерение |

Фоновый контроль связи каждые 3 с; UI проверяет состояние через SSE/REST каждые
2 с. Остановка симулятора не объявляет старые данные нормальными. Пока устройство
никогда не передавало данные и сбор не запрошен, показывается «Недостаточно данных».

Решение принимается только по текущей установке, без quality_flags, по трём
последним измерениям, каждое не старше таймаута. Старые и пришедшие не по порядку
пакеты сохраняются как история, но не вызывают текущую диагностику.

База — медиана последних до 30 корректных измерений за 10 минут, минимум 10.
Должна быть свежая связь, ненулевые RMS и обороты, коэффициент вариации RMS ≤ 15%,
сопоставимый режим и одинаковая полоса. Если указан температурный предел, его
достижение блокирует утверждение. Требуется явное действие администратора/главного
инженера, проверившего исправность. Сохраняются автор, время и ID исходных измерений.

Для относительного сравнения обороты должны отличаться от базы не более чем на
10%, нагрузка — не более чем на 15 процентных пунктов, полоса должна совпадать.
Иначе статус «Другой рабочий режим», а относительное правило не применяется.
Рабочие режимы в этом срезе задаются параметрами пакета, не определяются ML.
Универсальный вибрационный порог для всех двигателей не применяется.

Каждое непрерывное условие даёт одно событие. Повторные измерения обновляют
last_seen_at, а не создают новые предупреждения. Восстановление фиксируется
отдельно от решения человека. Если инженер закрыл событие при активном условии,
это не сбрасывает подавление: новое событие возможно только после восстановления
и нового подтверждённого превышения.

Осмотр обязателен для статуса «Подтверждено»/«Не подтвердилось», запись работ —
для «Устранено», результат — для «Закрыто». История решений не перезаписывается.
Статус измеренного состояния остаётся отклонением, даже когда событие закрыто,
если параметр ещё не восстановился.

Общий RMS = √(RMS_X² + RMS_Y² + RMS_Z²), единицы **g**, не мм/с. Сам по себе общий
RMS не позволяет назвать неисправность подшипника или процент вероятности отказа.
Причина в объяснении — «Причина не установлена». Уверенность и срок до отказа
не выдумываются. Симуляция проверяет программный конвейер, не точность диагностики
на промышленном оборудовании.

`analytics/signals.py`: RMS после полосового фильтра Butterworth, FFT с окном Hann,
частотное интегрирование g→м/с²→мм/с только внутри заданной полосы, без DC.
Эти функции проверяются известным синусоидальным сигналом. Входной API первой
версии принимает готовые признаки; диагностические waveform/FFT записи пока не
загружаются и на экране не имитируются. Базовые скользящие оценки — медиана,
вариация и окно подтверждения; сложный трендовый анализ — следующий этап.
